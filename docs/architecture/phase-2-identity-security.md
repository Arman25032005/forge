# Phase 2 — Identity + Security

## Scope delivered
- **Models**: `Organization` (tenant), `User` (with `Role` enum: ADMIN,
  ANALYST, OPERATOR, VIEWER, and a per-org unique email constraint),
  `AuditLog` (organization-scoped, records action/resource/outcome/context).
- **Authentication**: password hashing via `passlib[bcrypt]`; JWT access
  tokens (`pyjwt`, HS256) carrying `sub` (user id), `org_id`, `role`, `iat`,
  `exp`. Routes: `POST /auth/register-organization`, `POST /auth/register`,
  `POST /auth/login`, `GET /auth/me`.
- **Authorization (RBAC)**: permission primitives in
  `app/core/permissions.py` (`document.read`, `document.write`,
  `data.query`, `agent.execute`, `tool.execute`, `action.propose`,
  `action.execute`, `audit.read`, `user.manage`, `policy.manage`) mapped to
  the four roles. `require_permission(...)` is a FastAPI dependency used to
  gate routes server-side — `GET /audit/logs` is the first example.
- **Tenant context**: every authenticated request resolves an `AuthContext`
  (`user_id`, `organization_id`, `role`) from the verified token, and the
  role/active-status is **re-read from the database on every request**
  rather than trusted from the token — a role downgrade or deactivation
  takes effect immediately, and a forged role claim in the JWT is ignored.
- **Audit foundation**: `record_event()` writes tenant-scoped audit rows on
  registration and login (success and failure); `GET /audit/logs` returns
  only rows where `organization_id` matches the caller's own token — never
  a client-supplied tenant parameter.
- **Migration**: Alembic autogenerate produced
  `alembic/versions/ef7dfacfd921_create_organizations_users_audit_logs.py`
  for the three new tables; upgrade and downgrade were both executed
  against a throwaway SQLite database and completed without error.

## What was actually tested, and how
19 tests in `apps/api/tests/{test_auth,test_rbac,test_tenant_isolation}.py`,
run against an in-memory SQLite database (via `aiosqlite` + `StaticPool`)
through the real FastAPI app and dependency-injected DB session — not
mocks. All 19 pass; `ruff check`, `ruff format --check`, and `mypy app` are
clean.

## What was NOT tested (honest limitations)
- **No live Postgres was used for these tests** — SQLite (async, in-memory)
  stands in for it. The Alembic migration itself *was* run against a real
  SQLite database (upgrade + downgrade), but not against Postgres, since
  Docker/Postgres are unavailable in this environment (see Phase 1 report).
  The migration is generated by SQLAlchemy/Alembic from the same models
  used in tests, so the schema shape is the same, but dialect-specific
  behavior (e.g. Postgres's native `UUID`/`ENUM` types vs. SQLite's) has not
  been verified.
- **No OIDC/external identity provider integration** — this phase
  implements a self-contained password + JWT scheme that is structured to
  be OIDC-compatible later (separate token issuance from a pluggable
  identity source), but no actual OIDC provider has been wired up or
  tested.
- **No refresh tokens / logout / token revocation** — only short-lived
  access tokens exist. A stolen token remains valid until it expires
  (30 minutes by default). Revocation is not implemented in this phase.
- **Rate limiting on login/register is not implemented** — brute-force
  protection is deferred; noting it here rather than silently skipping it.
- **RBAC is currently role→permission only** (no per-resource ACLs or
  attribute-based policy). `policy.manage` exists as a permission constant
  but no policy-management endpoint exists yet.

## Gate status
Per the phase plan: "All critical security tests must pass." The specific
tests listed in the plan (invalid authentication, expired token, missing
permission, privilege escalation, cross-tenant access) are all implemented
above and pass. Rate limiting and token revocation are explicitly flagged
as not yet built, to be picked up alongside deeper security work in
Phase 9 (Red Team + Hardening).
